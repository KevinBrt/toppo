# Toppo architecture

> Modern issue tracking. Self-hosted. Free forever, no strings attached.

Toppo is a modern, self-hosted, forever-free issue tracker in the spirit of YouTrack, Mantis or Taiga. This document records the vision, the technical choices and every decision that shapes the code. Keep it current: the next contributor (human or Claude Code) starts from it.

## Principles

Read these before any decision.

1. **One edition, everything included.** No user or guest limit, no paid SSO, no feature reserved for a closed version.
2. **One-command install.** `docker compose up` starts Toppo and its PostgreSQL.
3. **A complete core, extended by plugins.** The core covers what most teams need, complete from install: nobody assembles thirty plugins to get a full tracker, so the kanban board, webhooks and GitHub are built in. Plugins answer what is specific to a team or a tool. The plugin system lands right after v1.0.
4. **Fast and beautiful.** Fluid UI, keyboard shortcuts, command palette, responsive down to phones.
5. **Maintainable by one person.** Few dependencies, strict conventions, tests at every step.
6. **Secure by default.** Strict CSP, least privilege everywhere, every input validated, every route authorized.
7. **Configurable, not hard-coded.** Workflows, properties, categories, priorities, labels and roles are data an admin edits, with sensible defaults.

## v1.0 scope

v1.0 lets a team replace Mantis day to day, nothing more.

**In scope**

- Local accounts (email + password) and a first-run wizard that creates the admin.
- Projects with a short key (`WEB`, `API`) and numbered issues (`WEB-42`).
- Issues: category, title, Markdown description, status, priority, assignee, reporter, labels, properties.
- Configurable workflows (statuses that close issues or not), global by default and overridable per project.
- Properties (Version, Team…), defined for the instance and adapted per project: each one shown in the issue list or not, asked at creation or not, then required or not.
- List view (sort, group), filters, full-text search.
- Comments, attachments, activity history per issue.
- In-app and email notifications.
- Custom roles composed from permissions; Administrator, Team and Requester are editable defaults, named in the administrator's language at setup. Requesters (customers, other departments) submit and follow their own issues in the same interface, seeing only those; the team sees every issue.
- Automated tests at every level, blocking in CI.

**Out of scope (later)**

- Kanban board, sprints, estimates, time tracking, Gantt, wiki.
- Plugin system and webhooks, then OIDC, SAML, LDAP: right after 1.0, free.
- Inbound email (create an issue by writing to an address).
- Real-time collaboration, native mobile apps, AI.
- Dark theme (the UI ships a single light theme; tokens make a second theme possible later).

## Repository layout

The server serves both the API and the compiled front end: one Docker image, one port.

```
toppo/
├── apps/
│   ├── server/        # Fastify: platform/ (http, auth, cqrs…) + features/ (routes, commands, queries)
│   └── web/           # React SPA (Vite): routes/, features/, shared/
├── packages/
│   ├── core/          # pure business logic: issues, workflows, permissions
│   ├── db/            # Drizzle schema, migrations, connection (PostgreSQL)
│   ├── shared/        # Zod schemas and types shared by front, back and plugins
│   ├── ui/            # design tokens and accessible components
│   ├── testing/       # test database setup, data factories
│   └── plugin-sdk/    # public plugin API, after v1.0 (npm: @toppo-tracker/plugin-sdk, MIT)
├── plugins/           # the reference plugin, after v1.0
├── e2e/               # Playwright tests, run against a build or the Docker image
├── scripts/           # repository guards run in CI (conventions, dependencies)
├── docker/            # Dockerfile, docker-compose.yml for users, compose.dev.yml
├── docs/              # user and plugin documentation
├── CLAUDE.md          # rules for Claude Code
└── ARCHITECTURE.md    # this document
```

Dependency rule: `core` depends on nothing but `shared`. Server, front end and plugins depend on `core`, never the reverse. Plugins import only `plugin-sdk`. The browser never bundles `db`. These rules are data in `scripts/src/dependencies/rules.ts` and fail CI when broken.

Key point: **every issue change writes an `activities` row in the same transaction.** It is the single source for history, notifications, webhooks and plugins. Rows written together read back in order: ids are UUID v7 with a counter within the millisecond.

`issues.properties` is a JSONB object keyed by property id, each value as its property's type stores it (`PROPERTY_VALUE_SCHEMAS` in `@toppo-tracker/shared`): an option's id for a list, an array of them for a multi-select, a line of text (500 characters), a number, a calendar day (`2026-11-02`, no time zone), someone's id, or `true` for a box ticked; no value is stored for none. `propertyValueOf` (`@toppo-tracker/core`) checks a value against the project's effective properties. It avoids a slow key-value table, and a GIN index (`jsonb_path_ops`) finds the issues having a value.

### Global defaults, project overrides

Two things can differ per project; everything else (categories, priorities, labels, roles) is one list for the whole instance, edited in the settings. A project may only hide the category or the priority, or require it at creation: their options stay the instance's.

**Workflows are copied.**

- The instance has one workflow (`project_id` null). A project without a workflow of its own follows it: add a status to it and every such project gets it at once.
- **"Customize for this project"** copies the instance's workflow into one the project owns, then edited freely.
- **"Revert to the global workflow"** deletes the project's copy. Issues on a status the instance's workflow lacks move first: the UI shows a mapping screen ("issues _In review_ move to…") and the server applies the mapping and the revert in one transaction, writing one activity per moved issue.
- Statuses are a shared catalog: the copy and the original share their status rows, so customizing moves no issue. A status added to a copy belongs to its project; the instance’s statuses a copy keeps are renamed, recolored or made closing in the settings only, and every copy follows.
- People change an issue’s status, never the system. The workflow says which statuses may follow each one (`workflow_transitions`), for everyone, administrators included, or lets any status follow any other (`free` mode, its transitions kept for when it is defined again). A project’s copy takes the transitions and the mode along.
- Saving a workflow is one transaction: a status taken out moves its issues to the status chosen, one activity per issue; a status that starts or stops closing issues closes or reopens them (`closed_at`); a status no workflow uses and no issue has is deleted. Creating or moving an issue reads the workflow under a shared lock, so a save never applies half-way under it.

**Properties are adapted one by one.**

- The instance defines properties (Version, Team…); every project gets them.
- A project adds properties of its own, hides one of the instance's, or gives it options of its own (its own versions), without touching the others (`project_properties`).
- Options of its own start as copies of the instance's: the project's issues move to the copies in the same transaction, so nothing is lost. Going back to the instance's options takes the project's off its issues, each told in its history.
- `effectiveProperties` (`@toppo-tracker/core`) works out what a project's issues take: the instance's properties it does not hide, with their options or its own, then its own properties. The form, the issue, the lists and the checks at creation all read it; a hidden property's values stay in `issues.properties`, unseen until it shows again.
- Each property says whether it shows in the issue list, whether it is asked at creation and, if so, whether it is required.

## Roles and permissions

Code always checks a permission, never a role name. A role is only a set of permissions that the admin composes freely, in a single list for the whole instance (one matrix in the settings), never defined per project.

- **Two levels, global default and project override**: a member's role grants its organisation permissions in the whole instance, and its project permissions in every project the member reaches; a project may give the member another role from the same list.
- **The system role** (Administrator, `grants_all`) has every permission, present and future. It cannot be edited or deleted, it is the only one that manages roles, and the instance always keeps an active member holding it.
- **A role is just a role**: there is no built-in kind of role. Requester is an ordinary role, which the admin renames, changes or deletes like any other; only the system role is special.
- **A role is deleted only once nobody holds it**: an active or deactivated member, a pending invitation or a project giving it blocks it, in the database too (`CHECK` constraints, `ON DELETE RESTRICT` on `project_members`). Deleted accounts and accepted invitations lose it (`ON DELETE SET NULL`). The screen says who still holds it.
- **Access to projects is given per member**: none until given, every project (`users.all_projects`, present and future), or chosen projects (`project_members`). It is chosen when inviting (none by default) and changed from the member or from the project; every project is given, taken or invited to only by someone who reaches every project, never by its holder on themselves (`403 ALL_PROJECTS_RESERVED`). The system role reaches every project, and takes no role of a project (`409 SYSTEM_ROLE_HOLDER`): it has every permission there anyway. A project's access list shows everyone: those who reach it automatically, its members, and the pending invitations that give it.

```ts
// Forbidden (rejected by `npm run check:conventions`)
if (member.role === 'admin') { … }

// Expected: the operation declares its permission, checked before its input is even read
export const inviteUser = defineCommand({
  name: 'user.invite',
  access: { permission: 'instance.users.manage' },
  …
});
```

**Rules**

- `can(permissions, permission)` in `core` decides. Commands and queries declare `access: { permission }`, checked before their input; a route declares the access of the operation it runs (`config: { access: operation.access }`, checked by `check:conventions`), enforced before the body is parsed. The server refuses to boot if a route forgets its access.
- Effective permissions in a project = the role the project gives the member, or else their own role (`projectPermissionsOf` in `core`). That role grants project permissions only: organisation permissions always come from the member’s own role. The system role keeps every permission in every project, whatever a project gives its holder. The actor's permissions are read with the user on every request (one query), so a role change applies at once. A stored permission the catalog no longer knows, or one only the system role may hold, grants nothing (`permissionsOfRole` in `core`).
- An operation about a project declares `access: { project: 'projectKey' | 'issueKey', permission? }`: the input field names the project, and comes from the route's path (the server refuses to boot otherwise), so a route checks it before reading the body. A project the actor does not reach answers 404 `PROJECT_NOT_FOUND`, as if it did not exist; one they reach without the permission, 403. The project, the actor's role and their membership are read in one query, and the operation gets the project with the actor's permissions there. An archived project is read-only: commands on it answer 409 `PROJECT_ARCHIVED`, unless their access allows it (`evenArchived`, to unarchive it).
- Managing a project's members gives no way to more rights: one may give there, and act on a member holding, only a role whose project permissions one holds there oneself, never the system role (`canGiveProjectRole`, `canActOnProjectMember` in `core`); otherwise 403 `ROLE_BEYOND_YOURS`. Someone given every project works in a project with their own role wherever it gives them none: giving them one there, or taking it away, also needs their own role within the actor's.
- An operation about an issue names it by key (`access: { project: 'issueKey' }`, `/api/v1/issues/WEB-42`): the project is resolved first, then the issue, which answers 404 `ISSUE_NOT_FOUND` to whoever does not see it (`issue.read`, or `issue.read.own` for their own issues). What one may do on an issue comes from `issueActionsOf` in `core`: whoever reported it may fix its title and description and attach files to it; whoever sees it may follow it; its fields, status, assignee and deletion need `issue.update`, `issue.assign` and `issue.delete`, on one's own issues too. Files follow the place they are attached to (`canAttachTo`, `attachmentActionsOf`): to a request, whoever may change its words attaches them, and its uploader (while they still may) or whoever has `issue.update` removes one; to a comment, its author attaches them, and whoever may delete the comment removes one. Whoever sees the issue downloads its files.
- A project route may also require an organisation permission, held through the member's own role, once the project is reached: deleting a project needs `project.delete` and answers 404 to those who do not reach it.
- The front end receives the instance permissions in `GET /api/v1/me` to hide what the user cannot do; the server stays the only judge.
- The instance always keeps an active member holding the system role: a deactivation or role change that would break this is refused, and such changes are serialized by an advisory lock.
- The matrix saves every changed role in one transaction. Each change carries what the matrix showed (`from`) and what it should grant (`to`); if a role changed meanwhile, the whole save is refused (`409 ROLES_CHANGED`) and the screen shows the other administrator's changes, rather than overwriting them.
- At most 20 roles (`ROLES_MAX`): the matrix shows them side by side and the list stays bounded. Creating and renaming roles lock the role rows, so the limit and the unique name hold under concurrency; giving a role share-locks it, so it cannot be deleted at the same moment.
- CI fails if code compares a role name (`check:conventions`).
- Plugins add their own permissions to the same catalog, named after them (`time-tracking.entries.log`), in a section of the matrix each: those of every plugin installed, read on each request (see the plugin system below).

## Plugin system (after v1.0)

Designed in [docs/plugins/design.md](docs/plugins/design.md), which holds the details, the measurements of its prototype and the steps; this section keeps its decisions. The core prepares for it already: every change goes through `activities` and the job queue, and the core's integrations build on blocks plugins will share.

- **A plugin** is TypeScript built by `toppo plugin build` into a zip, which an administrator uploads in **Settings → Plugins**. It imports only the published packages (`@toppo-tracker/plugin-sdk`, `@toppo-tracker/plugin-ui`, MIT). Its manifest is derived from its code, run in the sandbox when it is uploaded, never read from a file its author writes.
- **Its API**: `definePlugin`, `defineEntity`, `defineProperty`, then `plugin.defineAction`, `defineEventHandler`, `definePage`, `definePanel`, `defineRoute`, `defineJob`. Each takes one object; types flow from the objects, with no registration file. A plugin can be one file.
- **The sandbox**: a plugin's server code runs in QuickJS compiled to WebAssembly, one per plugin, in a worker thread, with a capped `WebAssembly.Memory` and deadlines. Its only door is `ctx`, checked on every call. The Node permission model was tried and rejected as a boundary.
- **Permissions**: `needs` (the core permissions it uses, approved by the administrator) and `permissions` (new ones, in the same catalog, prefixed with its id, held by the system role only until given). The catalog holds the permissions of every plugin installed, a pending one included: they open nothing while it does not run, and a save of the matrix keeps them. Those a plugin no longer declares, or all of its own once it is uninstalled, leave every role for good. Acting for a user takes both the user's access and the plugin's `needs`. Managing plugins is `instance.plugins.manage`, `systemOnly`.
- **Identity**: each plugin has a user of its own (`users.plugin_slug`), made at its first approval: no role, no password, no session (refused even if it had one), an address under `.invalid` that no reset email reaches, kept out of member lists, mentions and assignment. What a plugin writes shows as written by it.
- **Events** are Toppo's activity types. Recording activities queues one job for plugins when an enabled plugin hears of one of their types, people told of the change or not: bulk changes reach plugins too. That job hands each plugin the events of its projects, 10 per job, none a plugin made (plugins answering one another could never stop). Each event runs under a minute, retried alone with backoff; `{ once: event.id }` makes what the plugin writes single (`plugin_once_keys`, swept after a week). What it writes commits as it runs, not with the job.
- **Running**: each server process keeps a sandbox per plugin that ran lately, started from its package (read again and checked against its sha256), stopped after 10 minutes unused. A plugin acting as itself is an `Actor` with `plugin` set: `resolveProject` gives it its approved `needs` in its projects only, and nothing else; Toppo answers its calls (`ctx.issues.get`, `ctx.issues.comment`) with the features' own commands and queries. A run that fails counts against it; at 10 in a row it is disabled and those who manage plugins are emailed, in Toppo's words, never the plugin's.
- **Actions** run for the person signed in (`POST /api/v1/plugins/:pluginSlug/actions/:action`, 60 a minute per client, 64 KB of JSON). The access an action declares is checked first: an issue the person or the plugin does not see answers 404, so an action on an issue takes the need `issue.read`, which the manifest's schema checks (the build, the testing kit and the install refuse it otherwise). The plugin then acts with what both hold, the person's reach and permissions narrowed to the plugin's projects, needs and own permissions, and writes as itself. Its own Zod schema checks the input inside the sandbox, under 5 seconds, where a hostile pattern cannot hold Toppo up. A refusal answers 422 `PLUGIN_REFUSED` in its own words (a message key and its values), and counts as no failure; a plugin that fails answers 502, counted. Waiting on the plugin, the command holds no transaction (`defineDetachedCommand`).
- **Data**: entities attached to an issue or a project, stored by Toppo in one table with typed slots and seen as their issue or project is; properties of issues, of which those a plugin computes record no activity.
- **Screens**: React in a sandboxed frame with a CSP of its own (`connect-src 'none'`), talking to Toppo through a bridge.
- **Outbound HTTP**: declared hosts only, through a guard of the core shared with its integrations, never to an internal address.
- **Packages** are kept in the data volume (`/data/plugins/<slug>/<sha256>.zip`), their sha256 in the database; those no plugin names are swept every hour. Official plugins live in `plugins/`, without privilege, and are not in Toppo's image: an administrator installs each from its zip, as any other.
- **Installing** checks a zip before anything of it runs: `server.js` and `plugin.json` only, at most 50 MB, each file stopped as it unpacks past its limit (10 MB for the server bundle, 100 MB in all); then the manifest its code declares, read in a sandbox of its own, strict, for a plugin API this Toppo speaks and an id that is not a core resource. One install at a time, 50 plugins at most. A new plugin waits for an approval (`pending`), given with the projects it acts in. An upgrade that asks for more (a need, a permission or a wider one, an event) waits for a new one and stops meanwhile; one that asks for no more takes the approved version's place. Installs, approvals and removals are written to the server's log.
- **Its name and logo**: a plugin names itself and says what it does with keys of its own messages, shown in each language. Its logo, `logo.png` or `logo.webp` beside its `package.json`, is checked by its bytes by `toppo plugin build` and again by Toppo, which keeps it in the database and serves it (`GET /api/v1/plugins/:pluginSlug/logo`, sandboxed, at an address that changes with the package): every plugin's to those who manage plugins, those at work to the others. An SVG is refused, since it may carry script.
- **The contract**: `apiVersion` is semver; nothing breaks in a minor version, a break is a new major after a deprecation period. The packages are published to npm, by GitHub Actions, once the contract is complete (data and screens included).

## Self-hosted installation

Goal: from zero to a working Toppo in under 5 minutes, without reading docs. See `docs/self-hosting.md` and `docker/docker-compose.yml`.

- **One multi-arch image** (amd64 + arm64) on GitHub Container Registry: `ghcr.io/kevinbrt/toppo`. Tags: `X.Y.Z`, `X.Y`, `latest` on releases; `edge` and `sha-…` on every green `main`. SBOM and provenance attestations attached.
- **Hardened runtime**: distroless, no shell, user 65532, read-only root filesystem, all capabilities dropped, `no-new-privileges`.
- **Files in `/data`**: attachments and the secret key generated on first start (`secret.key`, mode 600; or `TOPPO_SECRET`). The database lives in its own volume. Backup = `pg_dump` + a copy of `/data`.
- **Automatic migrations** at startup, in one transaction, under a PostgreSQL advisory lock so that several starting instances never migrate twice; Toppo refuses to start if one fails.
- **First-run wizard** in the browser: create the admin and name the instance. It requires a one-time **setup code printed in the server logs** (or preset with `TOPPO_SETUP_CODE`, at least 12 letters or digits once dashes and spaces are dropped), so a fresh instance exposed on a network cannot be claimed by a stranger. It closes for good once the first administrator exists. SMTP settings come with email notifications (step 4).
- **Configuration through environment variables**, all prefixed `TOPPO_`, validated at startup (unknown `TOPPO_*` variables are rejected to catch typos), each readable from a file with the `_FILE` suffix (Docker secrets). Documented in `.env.example`.
- **`/health`** for Docker and reverse proxies: 200 when the database answers, 503 otherwise, no version or error details.

## UI/UX

- Design tokens (colors, radii, shadows, fonts) defined once in `packages/ui/src/theme.css`. The default Tailwind palette is disabled so components can only use tokens. Theme taken from the reference mockups: dark sidebar `#0B1012`, teal primary `#0F766E`, page `#F5F6F8`, white cards with `#E6E8EC` borders, Geist and Geist Mono (self-hosted).
- **Light theme only** for now.
- **Responsive, mobile first**: fixed sidebar from 1024 px, navigation drawer below; no horizontal scroll from 320 px; 44 px touch targets on coarse pointers; safe-area insets. Reading and commenting an issue on a phone must be comfortable.
- **Accessible**: WCAG 2.2 AA, checked by axe in end-to-end tests on desktop and phone.
- Search palette (`Ctrl/Cmd + K`, or the Search button of the top bar): the issues of every project one reaches, the pages one may use and a new issue. It is the one keyboard shortcut.
- Forms mark required fields with a red star beside the label (`Field required`), announced as required to screen readers; optional fields and lists that always hold a value carry none.
- Lists put in order are dragged by a handle, with a mouse, a finger or the keyboard, each move announced (`SortableList`). Settings edited as a whole (roles, workflow, options) stay local until saved at once, with an unsaved changes bar and a question before leaving the page.
- Optimistic updates: the UI reacts before the server answers.
- i18n from day one (English, French): no hard-coded string in components (checked). Typed messages: a missing key or parameter fails type checking.

## Security

- **CSP**: `default-src 'self'`, no inline script, no `unsafe-inline` or `unsafe-eval`, `frame-ancestors 'none'`. Runtime `<style>` tags (Radix scroll lock) are allowed through a per-request nonce: Vite writes a placeholder into `index.html`, the server replaces it on every page request and the app hands it to `get-nonce`. HSTS and `upgrade-insecure-requests` only when `TOPPO_URL` is HTTPS, so plain-HTTP LAN installs keep working.
- **Route contracts** enforced at boot: access rule on every route (`public`, `authenticated` or a permission), response schema on every `/api/` route. Responses are parsed through their schema, which strips undeclared fields. Access is checked before the body is parsed. Public routes that write are rate limited per client address (`config.rateLimit`), before the body is parsed.
- **Authentication** (Better Auth, email and password): passwords of 12 to 128 characters without composition rules, hashed with scrypt; sessions in an `HttpOnly`, `SameSite=Lax` cookie, `Secure` with the `__Secure-` prefix behind HTTPS; 30-day sliding sessions. Only sign-in, sign-out, session, password change and password reset are exposed (allowlist and routes of Toppo's own); public sign-up is off. Changing one’s password requires the current one, is validated by Toppo before Better Auth, limited to 5 attempts per 10 minutes, and always signs out every other device; the new session’s token stays in its cookie, never in the response body. Sign-in is limited to 5 attempts per minute per client, keyed on the address Fastify resolves (Better Auth's default trust in `X-Forwarded-For` is overridden). Telemetry is off.
- **Cross-site requests**: every state-changing request with a foreign `Origin` or a cross-site `Sec-Fetch-Site` is refused (CSRF, login CSRF included). After sign-in, the app only redirects to same-site paths.
- **Attachments**: a file is the raw body of its request (`application/octet-stream`, its name percent-encoded in `x-file-name`), streamed to disk once access is checked, refused before a byte is read without a length, beyond `TOPPO_ATTACHMENT_MAX_SIZE_MB` (20 by default) or with less than 1 GB free. Its extension names its type, among an allowlist (images, PDF, text, CSV, Office, OpenDocument: no SVG, HTML or archive), and its content must confirm it: signatures, the container of Office files, no NUL byte in text. Its name is cleaned (last segment, no control or bidirectional characters, NFC, 255 characters). Every file is served under `Content-Security-Policy: default-src 'none'; sandbox` and `nosniff`, as an attachment to download; only images and PDFs are also served inline (`showsInline`), for thumbnails and for the browser's own PDF viewer. The app shows images and text itself (text as a read-only box, never interpreted).
- **Errors**: one envelope (`{ error: { code, message, details? } }`); 5xx are generic, details stay in logs with the request id (`x-request-id`, generated server-side, never trusted from the client).
- **Supply chain**: exact versions, lockfile restricted to `registry.npmjs.org`, each entry to the tarball of the package and version it names (no aliases), with integrity hashes, install scripts disabled, licenses checked against an AGPL-compatible allowlist, `npm audit` and dependency review on PRs, Actions pinned by SHA, base images pinned by digest, Dependabot, CodeQL, OpenSSF Scorecard.
- Vulnerabilities are reported privately (`SECURITY.md`).

## Test strategy

No merge without green tests: a task is done only when its tests exist and pass in CI.

| Level             | Tools                                         | What                                                                               | When         |
| ----------------- | --------------------------------------------- | ---------------------------------------------------------------------------------- | ------------ |
| Unit              | Vitest, fast-check                            | `core` logic: permissions, workflows, numbering, validation                        | Every commit |
| API integration   | Vitest + `fastify.inject()` + real PostgreSQL | Each route: success, validation (400), unauthenticated (401), forbidden (403)      | Every PR     |
| Permission matrix | Vitest, generated from the catalog            | Each route refuses without its permission and accepts with it; default roles match | Every PR     |
| Components        | Vitest browser mode (Chromium)                | Behavior and accessibility, desktop and phone viewports                            | Every PR     |
| End-to-end        | Playwright (desktop + Pixel 7), axe           | First run, create and close an issue, comment, a member's access, a11y, responsive | Every PR     |
| Migrations        | Vitest                                        | All migrations on an empty database, then on each kept version's database          | Every PR     |

- Each integration test file gets its own database, cloned in milliseconds from a migrated template (`setupTestDatabase()`): tests run in parallel against a real PostgreSQL without seeing each other's data, and code that opens its own transactions (Better Auth) is tested as it runs in production. Locally, tests use their own PostgreSQL server (`test-db` in `docker/compose.dev.yml`), in memory and without fsync. The clones are dropped together once the run is over, never one by one while files still run: dropping a database waits for a checkpoint, which takes seconds while the other files write.
- End-to-end tests that change what every other test reads (the instance's workflow, its default category) are tagged `@instance`: they run alone, one at a time, once the desktop and phone tests are done.
- Data factories (`createUser()`, `createIssue()`…) shared in `packages/testing`.
- Coverage thresholds: `core` and `shared` 90 %, `server` 85 %, enforced in CI.
- Every fixed bug comes with the test that reproduces it.
